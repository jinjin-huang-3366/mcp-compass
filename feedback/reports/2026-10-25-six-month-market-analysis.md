# MCP Compass: six-month ecosystem evidence review

Period reviewed: 2026-04-25 through 2026-10-25. Prepared 2026-10-25.

## Scope and confidence

This is a **curated, directional review**, not a complete census of MCP feedback or a measurement of MCP Compass users. The local collector sampled the configured `modelcontextprotocol/registry` Discussions and the current Hacker News new/Show/Ask feeds. For this review, I also inspected public primary discussions in `modelcontextprotocol/modelcontextprotocol` and the Registry. The collector caps GitHub to the 30 most recently updated discussions per configured repository and HN to 30 current IDs per feed, so `--since 180d` does **not** retrieve every item published over six months. HN has no six-month historical coverage through those feed snapshots. Reddit remains disabled. Many measured claims below are published by discussion authors and have not been independently replicated here.

The `collect --since 180d` run returned **977 sampled source items** (115 GitHub, 862 HN; no source errors). After `analyse`, local state held **36 evidence records** (24 newly added in this run), all in GitHub-origin clusters, and **zero reply opportunities**. The generated local report is `.local/feedback/reports/feedback-intelligence-2026-10-25.md`. Its six deterministic clusters are screening aids, **not six validated recurring problems**: for example, “general MCP ecosystem friction” combines unrelated Registry operations and safety topics, while some auth and capability labels absorb adjacent but different reports. Its candidate counts and 7/30-day changes must not be read as market prevalence or reliable trends. The curated recommendations below are based on the linked source discussions, not those automatic candidate labels.

Ranking considers direct relevance to MCP Compass's *select an existing server, understand the evidence, then generate only if needed* workflow, severity of the failure, independence of the reports, and the gap between the report and the [documented current product](../../docs/marketing/LAUNCH_PACKAGE_V1.md). This is not a vote count. A proposal is not treated as a customer request. The [V0.8 plan](../../PLANS.md#v08--evidence-backed-server-selection) now turns these directions into reviewable tasks, not shipped features.

## Strongest signals

- **“Listed” is not “usable.”** A [Registry-wide read-only probe](https://github.com/modelcontextprotocol/registry/discussions/1591) reported 8,235 of 15,329 remote URLs completing `initialize` and `tools/list`; 3,617 returned 401/403 before listing. A separate [endpoint survey](https://github.com/modelcontextprotocol/modelcontextprotocol/discussions/3303) found many auth-gated hosts and explicitly distinguished *listable* from *callable* capabilities. These are different authors and methods. Authentication gates must not be called dead endpoints; a successful listing is not a safety guarantee.
- **Declared capability is weaker than enforced capability.** A [runtime annotation experiment](https://github.com/modelcontextprotocol/modelcontextprotocol/discussions/3299), a [call-argument approval-bypass incident](https://github.com/modelcontextprotocol/modelcontextprotocol/discussions/3203), and a [runtime-verification proposal](https://github.com/modelcontextprotocol/modelcontextprotocol/discussions/3211) all distinguish descriptions or hints from what a server can actually do. Only the incident is a direct operational failure report; the proposal is exploratory.
- **Selection has a tool-catalog cost.** One developer describes [task-specific routing before model inference](https://github.com/modelcontextprotocol/modelcontextprotocol/discussions/3269); another [benchmarked the `tools/list` token cost](https://github.com/modelcontextprotocol/modelcontextprotocol/discussions/3176). This supports improving selection and explanation, not automatically building a new runtime router.
- **Validation and setup fail in distinct ways.** A [30-entry stdio pilot](https://github.com/modelcontextprotocol/modelcontextprotocol/discussions/2733) reports nine pre-initialization exits from yanked or superseded packages. MCP Compass already has an isolated validation worker, but [hosted jobs remain queued without a separate worker deployment](../../docs/DEPLOYMENT.md#validation-worker). This is a verified MCP Compass product gap, not evidence of user adoption.
- **Trust is layered.** Two independent Registry discussions distinguish [publisher identity from artifact provenance](https://github.com/modelcontextprotocol/registry/discussions/1463) and propose [attestation binding](https://github.com/modelcontextprotocol/registry/discussions/1478). A [tool-description survey](https://github.com/modelcontextprotocol/registry/discussions/1591) reports concealment-style instructions on some hosts. None of these justifies a blanket “safe server” badge.

### Direct operator-provided Reddit feedback

The [comment on the operator's Reddit post](https://www.reddit.com/r/mcp/comments/1wmrqiq/comment/pb9vjhh/) says that a Registry entry calling itself read-only is self-description, and that declared tools help shortlist servers but cannot establish that a write path is unreachable. In a follow-up on the same thread, the **same commenter** describes server-enforced read-only credentials and a sandbox probe as a stronger check. This is one author in one thread, manually verified outside the disabled Reddit collector; it does **not** change the 36 automated evidence records above or count as two independent reports. It sharpens rank 3 and motivates [EVI-01 through EVI-03](../../PLANS.md#v08--evidence-backed-server-selection). Schema inspection can reveal hidden or ambiguous write surfaces; even a bounded live probe demonstrates only the tested conditions, not universal unreachability.

Ranks 1–5 are the best near-term investigations. Ranks 6–10 are narrower or lower-confidence; validate them before assigning build work. Priority is qualitative, not a promise to implement.

## What not to build yet

- Do not build a generic “MCP safety score” that implies verified enforcement. The cited studies inspect different layers, and `tools/list` does not prove a tool cannot be called.
- Do not build an autonomous server-execution crawler or test write-capable tools. Any runtime validation belongs in the existing isolated worker with explicit limits, no ambient credentials, and no side-effecting calls by default.
- Do not prioritize pricing/SLA fields, attestation standards, or a new tool router as commitments from one or two discussion threads. First test whether MCP Compass users need them and whether reliable data exists.
- Do not turn the earlier automatic “general MCP ecosystem friction” cluster into a roadmap item. It mixed unrelated reports and is not an underlying problem.

## Suggested next evidence checks

1. Run a small, consent- and rate-limit-aware audit of a representative sample of MCP Compass search results. Measure how often the current top-three results are reachable, auth-gated, setup-complete, or falsely classified; publish only aggregate results.
2. Ask 5–10 active MCP client/server developers which *selection decision* they recently could not make, what evidence was missing, and whether it blocked adoption. Keep answers linked to their original source or consented interview notes.
3. Extend research coverage before interpreting frequency or trend: paginate GitHub Discussions/issues by creation date across selected primary repositories, and use a compliant historical HN source if historical HN coverage is needed. The current HN feed adapter cannot answer “how many reports appeared over six months.”

No public replies or issues were created by this review. The linked plan tasks require normal implementation review and testing; no feature is complete or safety-certified by being planned.
