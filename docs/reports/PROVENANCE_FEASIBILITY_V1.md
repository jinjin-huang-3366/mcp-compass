# EVI-07: provenance explanation feasibility

Evaluated 2026-10-25 against the current MCP Compass ingestion model and the public Registry/package documentation. This is a design and fixture evaluation, not a live package audit or a deployed provenance feature. The eight [synthetic cases](../fixtures/provenance/cases.json) are deliberately controlled observations; `test_cases.py` exercises their expected boundaries offline.

## Evidence available today

| Question | Current source | What it supports | What it does not support |
| --- | --- | --- | --- |
| Who published this Registry name? | Official Registry response wrapper, server `name`, publication rules | The official Registry authenticates a GitHub or domain namespace at publication and checks package ownership. A correctly sourced response can say “listed under an authenticated Registry namespace.” | Identity of the human maintainer, continuous control of the namespace, current package safety, or independent re-verification of historical publication. A copied `_meta` object alone is not proof of origin. |
| Is this the package for this server? | `packages[*].registryType`, `identifier`, `version`, and package-type ownership marker such as npm `mcpName` | Exact coordinates and a package marker matching the Registry name can corroborate the Registry-to-package link. | A server name equal to a package marker is not a source-code link or evidence that the package behaves as described. Re-checking current package metadata may differ from the Registry's publication-time check. |
| Is this the advertised source repository? | Publisher-declared `repository.url`; package repository claim when present | Matching declarations are useful navigation and an explicit “both claim the same source” explanation. | A matching URL or GitHub enrichment of that URL does not prove the released package was built from that repository or commit. |
| Is this exact artifact intact or source-attested? | Optional publisher `fileSha256` (required for MCPB); package registry integrity metadata; provider-specific attestations if available | After fetching exact bytes in a bounded isolated verifier, a hash comparison can detect a mismatch. A cryptographically verified attestation can bind the *observed digest* to a build source identity. | The current ingestion fetches no package bytes, checks no registry integrity record, and verifies no signatures. A publisher-authored digest or merely present attestation is not independent verification. No one attestation format covers all package types. |

The [Registry schema](https://github.com/modelcontextprotocol/registry/blob/main/docs/reference/api/openapi.yaml) exposes package coordinates, optional `fileSha256`, and repository metadata. The [official Registry requirements](https://github.com/modelcontextprotocol/registry/blob/main/docs/reference/server-json/official-registry-requirements.md) describe namespace authentication, package ownership checks, and the difference between registry-managed and publisher-provided metadata. [Package-type rules](https://github.com/modelcontextprotocol/registry/blob/main/docs/modelcontextprotocol-io/package-types.mdx) vary: for npm, `mcpName` in `package.json` must match the server name; other ecosystems use different markers. [npm provenance](https://docs.npmjs.com/viewing-package-provenance/) and [GitHub artifact attestations](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations) offer narrower, provider-specific verification paths; a verified build provenance is not a security verdict.

MCP Compass currently retains raw Registry JSON, a boolean for an official metadata object, a publisher-declared repository URL, package and remote counts, and optional GitHub repository enrichment. `RegistryPayloadMapper` does not normalize exact package coordinates, package-side ownership markers, digests, or attestations. `McpServerEntity` stores only latest metadata. Its `official_registry_provenance` boolean is derived from the presence of a nonempty response metadata object; it must not be relabelled as independent authentication of arbitrary imported JSON. GitHub repository enrichment describes the declared repository, not a released package.

## Fixture result and user-visible example

The fixture suite keeps the three questions separate. `linked-attested` yields namespace authenticated, package name and source declarations aligned, digest matched, and a *simulated* verified attestation with matching subject and source. `missing-evidence` remains unconfirmed or unobserved. `package-name-mismatch` and `source-claim-mismatch` expose different linkage failures. `tampered-download` detects a digest mismatch. `attestation-subject-mismatch`, `attestation-source-mismatch`, and `unverified-attestation` reject distinct attestation failures even while the Registry namespace remains authenticated.

Concrete before/after decision: for `io.github.alice/weather`, the existing `officialRegistryProvenance: true`, `repositoryUrl: https://github.com/alice/weather`, and `packageCount: 1` could be read as one trust signal. In `tampered-download`, the namespace remains Registry-authenticated and the package marker matches, but the observed artifact SHA-256 is `bbbb…` versus the declared `aaaa…`. A future explanation should show “Registry namespace authenticated; package name linked; artifact digest mismatch; source build unverified,” never a combined “safe” badge. These are hypothetical fixture values, not observations about a real package.

## Decision

**Go** for a later, clearly separated explanation of *declared* Registry namespace, exact package coordinates, and declared source URL from persisted official-response data. Do not present the existing boolean as an end-to-end verified provenance result. Show collection time and origin; distinguish absent evidence from mismatch. A follow-up implementation would need to normalize per-package coordinates and evidence provenance while leaving raw metadata intact.

**No-go now** for an artifact-integrity or source-build verification status in search, ranking, or a generic safety badge. A credible pilot first needs a package-type-specific, read-only verifier for exact artifact bytes, package registry metadata, and a verified attestation subject/source identity where available. It must pin coordinates, cap bytes/time, avoid package installation or execution, preserve verification method and time, and report missing or unsupported evidence as unknown. Do not make any attestation standard mandatory across the catalog. Remote-only servers and unavailable package sources remain unknown for artifact linkage. If a pilot demonstrates useful coverage and low false claims, propose a separately scoped implementation task with an ADR for storage, freshness, and UI semantics.

## Reproduce

From the repository root, run `python -m unittest discover -s docs/fixtures/provenance -p 'test_*.py' -v`. All eight cases and the independence check should pass. The cases use simulated digest and attestation observations; they do not contact registries, fetch artifacts, or validate cryptographic signatures.
